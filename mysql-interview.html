01

索引INDEX

索引是 MySQL 面试的第一战场。B+ 树原理、失效场景、覆盖索引几乎是必考三连，务必能画出结构图。

1
为什么 InnoDB 选择 B+ 树做索引结构？对比 B 树、哈希、二叉搜索树各有什么问题？
高频必考原理
简答版（30 秒）
  • B+ 树的核心优势：非叶子节点只存键不存数据，单页能放更多键，树更矮胖（3~4 层支撑千万级行）；叶子节点存全部数据且用双向链表串联，范围查询和排序只需顺着链表扫。
  • 对比 B 树：数据分散在所有节点，单页放的键少、树更高；且范围查询要中序回溯，B+ 树直接沿叶子链表扫。
  • 对比哈希：哈希等值查询 O(1) 很快，但不支持范围查询和排序，也不支持最左前缀匹配。
  • 对比二叉/红黑树：二叉树每个节点只有 2 个分支，数据量大时树太高（百万级要 20 层），每层都是一次磁盘 IO，代价不可接受。
🔍 面试官可能追问
  • 一张表 2000 万行，B+ 树大概几层？怎么估算的？（按 16KB 页 ÷ 键大小算扇出）
  • 为什么建议用自增主键？（避免页分裂、写入接近顺序写）
  • 跳表（Redis zset）和 B+ 树的取舍？为什么 Redis 用跳表不用 B+ 树？
  • 聚簇索引和二级索引在 B+ 树上存的内容有什么区别？

2
哪些 SQL 写法会导致索引失效？平时怎么验证？
高频必考实战
简答版（30 秒）

常见的失效场景有六类，验证方式是 EXPLAIN 看 key 是否命中、type 是否为 ALL：

  • 最左前缀被破坏：联合索引 (a,b,c) 只用 b 查、或条件里对 a 用了范围后 c 失效；
  • 对索引列做函数或运算：YEAR(create_time)=2026、id+1=10；
  • 隐式类型转换：字符串列用数字查（phone = 13800000000），相当于套了一层 cast 函数；
  • 左模糊：LIKE '%xx' 前缀不确定，无法走 B+ 树有序性（'xx%' 可以走）；
  • OR 连接了非索引列（两列都有索引时可以走 index merge）；
  • 不符合取值比例：优化器估算回表成本高于全表扫描时主动放弃（大表的 !=、NOT IN 常见）。

最后一点值得主动强调：索引失效不一定是写法问题，也可能 是「统计信息不准 / 区分度低 / 回表成本高」导致的优化器主动放弃——这句能让面试官知道你真的排查过。

🔍 面试官可能追问
  • LIKE '%xx%' 一定不能走索引吗？（覆盖索引下可全索引扫描；或虚拟列 + 前缀索引）
  • NOT IN、!= 一定不走索引吗？（结果集小时可以走，优化器看成本）
  • 隐式转换具体是怎么让索引失效的？字符串列和数字列，哪边转哪边？
  • 怎么让统计信息更新？(ANALYZE TABLE)
3
什么是回表和覆盖索引？为什么说覆盖索引能显著提升查询性能？
高频必考原理
简答版（30 秒）

InnoDB 二级索引的叶子节点存的是「索引列 + 主键值」，不存整行。回表：通过二级索引找到主键后，还要再去聚簇索引里取完整行，等于查两棵树。覆盖索引：查询需要的字段全部包含在索引里，直接从索引就拿到结果，省掉回表。

收益有两层：一是省去回表的随机 IO（这是主要收益）；二是索引体积远小于整行，同样页数能缓存更多数据。判断方法：EXPLAIN 的 Extra 出现 Using index 就是覆盖索引。

🔍 面试官可能追问
  • 常见实战：查手机号是否存在，SELECT id FROM user WHERE phone = ? 建什么索引最优？
  • 为什么 SELECT * 是坏习惯？（几乎不可能覆盖索引，且破坏网络/存储）
  • 索引下推（ICP）是什么？5.6 引入后对回表有什么影响？（在存储引擎层先过滤，减少回表次数）
4
联合索引 (a, b, c) 的顺序怎么设计？谈谈你的索引设计方法论。
设计区分度题
简答版（30 秒）

核心原则：「最左前缀」匹配下，把查询最多、区分度最高的列放前面；等值列在前、范围列在后（范围条件之后的列停止走索引）。同时结合实际业务 SQL 统计：优先为高频、高并发查询建；考虑覆盖索引让常用查询免回表；避免冗余索引（已有 (a,b) 就不必再建 (a)）；长字符串用前缀索引控制长度。

索引不是越多越好：每个索引都是一棵 B+ 树，拖慢写入、占空间，优化器选择成本也变高。单表建议控制在个位数。

🔍 面试官可能追问
  • 区分度怎么算？（COUNT(DISTINCT col)/COUNT(*)，经验值 > 0.1 更佳）
  • WHERE a=1 ORDER BY b，联合索引怎么建能避免 filesort？((a,b)，排序也走索引有序性)
  • 前缀索引的长度怎么选？有什么代价？（无法覆盖索引、无法做 ORDER BY 优化）
  • 建索引有什么副作用？写入路径上发生了什么？
02

事务TRANSACTION

ACID 的「实现方式」和隔离级别是事务的两条主考线。答出「是什么」只能及格，答出「InnoDB 怎么实现的」才有竞争力。

5
ACID 分别是什么？InnoDB 靠什么机制实现每一个特性？
高频必考原理
简答版（30 秒）

ACID 是事务的四个特性，InnoDB 每个特性都有明确的落地机制——这是本题的加分点：

  • 原子性 A：undo log（回滚日志），失败时按 undo 逆向补偿回滚；
  • 持久性 D：redo log（重做日志），WAL 先写日志再刷脏页，崩溃后重放恢复；
  • 隔离性 I：MVCC + 锁，读靠多版本快照，写靠行锁 / 间隙锁；
  • 一致性 C：是最终目的，由 A、I、D 加上应用层约束（外键、唯一约束、业务逻辑）共同保证。
🔍 面试官可能追问
  • redo log 和 binlog 都是日志，为什么要有两个？
  • undo log 既然能恢复数据，为什么还需要 redo log？（一个是逻辑反向操作 vs 物理页重放，性能差异）
  • WAL 是什么思想？为什么先写日志比先刷数据页快？（顺序写 vs 随机写）
6
讲讲四个事务隔离级别，分别解决什么并发问题？InnoDB 默认用哪个？
高频必考概念
简答版（30 秒）

并发事务有三类问题：脏读（读到别人未提交的数据）、不可重复读（前后两次读同一行值不同，他人 update 提交）、幻读（前后两次范围查询行数不同，他人 insert 提交）。四个级别逐级解决：

  • 读未提交 RU：什么都不防，有脏读；
  • 读已提交 RC：防脏读（Oracle / PG 默认）；
  • 可重复读 RR：再防不可重复读，InnoDB 默认级别，且通过 MVCC + Next-Key 锁基本解决幻读；
  • 串行化：全部加锁串行执行，最安全性能最差。

一句话收尾：MySQL 的 RR 与 SQL 标准的 RR 不完全一样——标准 RR 允许幻读，而 InnoDB 的 RR 借助 Next-Key 锁在当前读下也能防幻读。

🔍 面试官可能追问
  • 为什么互联网公司（尤其阿里系规范）常把默认级别改成 RC？（减少间隙锁、降低死锁概率，Binlog 需改 ROW 格式）
  • RC 和 RR 下 MVCC 的 ReadView 生成时机有什么区别？（见第 12 题）
  • 怎么查看和设置隔离级别？(SELECT @@transaction_isolation)
7
MySQL 的 RR 隔离级别真的能完全避免幻读吗？
高频陷阱题原理
简答版（30 秒）

分两种读法回答。RR 下 InnoDB 用两套手段防幻读：

  • 快照读（普通 SELECT）：靠 MVCC，ReadView 在事务第一次读时生成并沿用，后续读的始终是同一快照，看不到别人新插入的行；
  • 当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）：靠 Next-Key Lock（行锁 + 间隙锁）锁住范围，别人无法在范围内插入。

但混用两种读法时幻读仍会发生：先快照读（不建锁），别人 insert 并提交，再当前读——这时就能看到「幻影行」了。先当前读再快照读，也能看到已提交插入。所以标准答案是：基本防住，但不能 100% 防。

🔍 面试官可能追问
  • 举一个具体能复现幻读的 SQL 序列（两个 session 交错执行的例子）
  • 要彻底防幻读怎么办？（事务一开始就用 SELECT ... FOR UPDATE 锁住范围，或升级到串行化）
8
redo log、undo log、binlog 各起什么作用？两阶段提交是干什么的？
高频必考原理
简答版（30 秒）
  • redo log：InnoDB 引擎层物理日志，保证持久性，崩溃恢复时重放已提交的修改；循环写、固定大小；
  • undo log：InnoDB 逻辑日志，保证原子性（回滚）+ 是 MVCC 版本链的载体；
  • binlog：Server 层逻辑日志，用于主从复制和数据恢复，追加写，有 STATEMENT / ROW / MIXED 三种格式。

redo log 和 binlog 是两个独立的日志系统，一个事务可能「redo 写了、binlog 没写」。两阶段提交就是让它们保持一致：redo log 先写 prepare → 写 binlog → redo log 置为 commit。崩溃恢复时：redo 处于 prepare 且 binlog 完整 → 提交；binlog 不完整 → 回滚。这样保证「要么两边都成功，要么都失败」。

🔍 面试官可能追问
  • 组提交（group commit）了解吗？为什么 5.7/8.0 提交性能大幅提升？
  • redo log 写满了会发生什么？（刷脏页，业务写入被阻塞，check point 机制）
  • binlog 的 ROW 和 STATEMENT 格式各有什么优缺点？主从复制用哪种？为什么？

03

MVCCMULTI-VERSION CONCURRENCY CONTROL

MVCC 是 1-3 年面试的「分水岭」题：答得出 ReadView 判定规则基本直接过，答不出基本挂。建议整节背诵。

9
什么是 MVCC？它解决了什么问题？由哪几部分实现？
高频必考核心分水岭
简答版（30 秒）

MVCC 是多版本并发控制：普通读操作不加锁，而是读取数据的一个历史版本快照，从而实现「读写不冲突」——读不阻塞写、写不阻塞读，大幅提升并发性能。

InnoDB 的 MVCC 由三部分协作实现：

  • 隐藏列：每行有 trx_id（最后修改它的事务 id）和 roll_pointer（指向 undo log 里的旧版本）；
  • undo log 版本链：每次修改都把旧版本留在 undo log 里，通过 roll_pointer 串成链；
  • ReadView（读视图）：事务做快照读时的「活跃事务名单」，决定当前能看到链上哪个版本。
🔍 面试官可能追问
  • 「读写不冲突」相比纯锁方案性能好在哪里？
  • MVCC 只在 RC 和 RR 两个级别下生效，为什么 RU 和串行化不需要？
  • update 会不会新建版本？删Delete 呢？（删除是打 delete mark，purge 线程物理清理）

10
RC 和 RR 的 ReadView 生成时机有什么区别？这带来了什么效果差异？
高频必考原理
简答版（30 秒）

这是 RC 和 RR 实现差异的本质，就一句话：

  • RC（读已提交）：每次 SELECT 都重新生成一个 ReadView —— 别人提交了就能看到，所以「不可重复读」；
  • RR（可重复读）：事务内第一次 SELECT 时生成，之后整个事务复用 —— 无论别人提交多少次，看到的都是同一快照，所以「可重复读」。

换句话说，RR 的「可重复读」不是锁出来的，而是把 ReadView 冻结在事务第一次读的时刻实现的。

🔍 面试官可能追问
  • 「事务开始」和「第一次快照读」是一回事吗？(BEGIN 不会立刻生成 ReadView，START TRANSACTION WITH CONSISTENT SNAPSHOT 才会)
  • RR 下事务开启很久后查询，为什么数据「停在旧时刻」？ undo 链很长会不会有问题？（会，见 Q12）
11
快照读和当前读的区别是什么？哪些 SQL 是当前读？
概念联动 Q7
简答版（30 秒）

快照读：读 MVCC 的历史版本，不加锁。就是普通 SELECT（RC/RR 下）。

当前读：读最新已提交版本，并对记录加锁。所有修改语句隐含当前读，显式当前读是 SELECT ... FOR UPDATE / FOR SHARE。例如 UPDATE t SET x=x+1 必须基于最新值加 1，不能基于快照。

两者混用正是 RR 下幻读残留的根源（呼应第 7 题）。

🔍 面试官可能追问
  • UPDATE 修改的是快照还是最新版本？如果目标行已被别的事务改过会怎样？（当前读 + 行锁阻塞等待）
  • FOR UPDATE 和 FOR SHARE（8.0 前叫 LOCK IN SHARE MODE）加的锁有什么区别？
  • 半一致读（semi-consistent read）听说过吗？（RC 下 update 的优化）
12
为什么长事务危害大？它和 MVCC、undo log 有什么关系？
实战综合题
简答版（30 秒）

长事务有三大危害，前两个都和 MVCC 直接相关：

  • undo 无法清理：一个 RR 事务长时间不提交，它持有的 ReadView 之前的所有 undo 版本都不能被 purge 线程删除，undo 表空间持续膨胀，版本链越拉越长，所有访问该行的查询回溯成本变高；
  • 锁长期持有：行锁、间隙锁在事务结束才释放，并发度骤降、死锁概率上升；
  • 主从延迟：大事务 binlog 传输和回放都是大块操作，8.0 之前大事务提交还会卡顿。

排查：information_schema.innodb_trx 看 trx_started；治理：拆小事务、避免事务里放 RPC/IO、监控自动提交配置。

🔍 面试官可能追问
  • 怎么找出当前运行最久的几个事务？（SELECT ... FROM information_schema.innodb_trx ORDER BY trx_started）
  • 为什么「事务里调外部接口」是反模式？怎么改？
  • purge 线程什么时候干活？undo 表空间膨胀过大还能缩回去吗？（8.0 支持自动 truncate）
04

锁机制LOCK

锁的考察重点是「加锁范围」——尤其是间隙锁。死锁案例题建议提前准备一个自己亲历的故事。

13
InnoDB 有哪几种行级锁？Record Lock、Gap Lock、Next-Key Lock 分别锁什么范围？
高频必考原理
简答版（30 秒）
  • Record Lock（记录锁）：只锁索引上的一条记录；
  • Gap Lock（间隙锁）：锁两条索引记录之间的开区间，只挡 insert，别的事务可以互相持有同一间隙的锁；
  • Next-Key Lock：记录锁 + 前面的间隙，即左开右闭区间 (a, b]，是 RR 下加锁的默认单位，用来防止当前读下的幻读。

补充一个高频细节：唯一索引等值查询命中记录时，Next-Key Lock 退化为纯 Record Lock；未命中时退化为 Gap Lock（锁住它本应所在的间隙）。

🔍 面试官可能追问
  • RR 是默认加 Next-Key Lock 的，什么场景下会退化？（如上；以及 RC 下没有 Gap/Next-Key）
  • 插入意向锁（insert intention lock）是什么？和 Gap Lock 什么关系？
  • 间隙锁只在 RR 下存在吗？RC 下为什么没有？（RC 用最新读解决脏读，不需要防幻读）

14
「UPDATE ... WHERE 非索引列」为什么危险？InnoDB 的加锁规则和索引是什么关系？
高频必考实战
简答版（30 秒）

核心结论：行锁是加在索引上的。

  • WHERE 条件没走索引：行锁无处安放，退化为给全表所有记录加 Next-Key Lock，等价于锁全表，并发全挂；
  • 走联合索引：按索引扫描到的范围加锁。索引前缀能定位多少，就锁多少，前缀失效的部分继续向后扩；
  • 走唯一索引等值命中：只锁这一条（Record Lock）；普通索引等值：向右扫到第一个不满足的值为止，最后一个还会补 Gap Lock。

所以「update 无索引列」和「RR 大范围间隙锁」是生产上批量误伤 / 死锁激增的前两名。

🔍 面试官可能追问
  • 两个事务分别 update 不同主键，会互相阻塞吗？（不会；但如果查询条件无索引，会全表锁而互相等）
  • 怎么看当前持锁和等待？（performance_schema.data_locks / data_lock_waits，8.0）
  • 唯一索引等值未命中、普通索引等值命中，分别锁什么范围？（Gap Lock / 多条 Record + 末端 Gap）
15
讲一个死锁场景：怎么产生的、怎么排查、怎么解决？
高频必考案例题
简答版（30 秒）

经典场景——两个事务相反顺序更新两条记录：事务 A 先 update id=1 再要 id=2；事务 B 先 update id=2 再要 id=1，互相持有对方需要的锁，形成环状等待。InnoDB 检测到「等待图」成环后，回滚代价较小的事务并报 Deadlock found 错误（1213）。

更隐蔽的一类是 Gap Lock 引发的插入死锁：两个事务先 SELECT...FOR UPDATE 没查到 → 都持有同一 Gap 锁（间隙锁相容）→ 都去 INSERT → 各自等待对方释放间隙 → 死锁。

排查：SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK 段，包含两个事务的 SQL 和持有的锁。

预防四板斧：① 按固定顺序访问资源（如统一按主键升序）；② 小事务、尽快提交；③ 减少 RR 下的范围条件触发间隙锁；④ 必要时用 RC 或显式锁替代隐式范围锁。

🔍 面试官可能追问
  • InnoDB 死锁检测（waits-for graph）和锁等待超时（innodb_lock_wait_timeout）两条路有什么区别？
  • 高并发热点行更新有什么优化思路？（拆行、队列化、CAS 乐观锁、降隔离级别）
  • 拿到 1213 错误之后业务上应该怎么处理？（捕获重试，注意幂等）

乐观锁和悲观锁的区别？在业务里怎么选？
概念 + 设计
简答版（30 秒）

悲观锁：假设冲突频繁，取数据时就加锁，别人阻塞等待。数据库层就是 FOR UPDATE；适合写多、临界区复杂、必须串行的场景（账户冻结、库存扣减热点行）。

乐观锁：假设冲突少，不加锁，更新时校验版本——UPDATE t SET x=?, version=version+1 WHERE id=? AND version=?，影响行数为 0 说明别人改过，业务重试或报冲突。适合读多写少、可重试的场景（CMS 内容、订单状态流转）。

选择依据：冲突概率低选乐观（省锁开销），冲突高选悲观（避免大量重试空转）；热点极端场景两者都退化，要走队列 / 缓存扣减 / 拆分热点。

🔍 面试官可能追问
  • 乐观锁的 ABA 问题在 MySQL 会出现吗？（用单调 version 就没有；用状态字段可能「绕一圈回来」）
  • 秒杀扣库存用悲观锁还是乐观锁？怎么扛住热点？（预扣 + 异步落库 / Redis 原子扣减再同步 DB）

线上一条 SQL 突然变慢，你的完整排查思路是什么？
高频必考体系题
简答版（30 秒）

分四步闭环：发现 → 定位 → 分析 → 优化。

  • 发现：慢查询日志（slow_query_log=ON，long_query_time 按业务定，线上常设 0.5~1s；也可接 PMM / 阿里 DAS 类监控）；
  • 定位：pt-query-digest 聚合出 TOP N 慢 SQL（按总耗时排序而非单次）；
  • 分析：EXPLAIN 看 type、key、rows、Extra；确认是否走索引、回表量、filesort / temporary；
  • 优化：按层面改——SQL 写法 / 加或改索引（覆盖索引、联合索引）/ 表结构（字段类型、大字段拆分）/ 参数（buffer pool）→ 极限场景才上缓存、读写分离、分库分表；
  • 验证：上线前后对比执行计划与耗时，监控回归。
🔍 面试官可能追问
  • SQL 一直很快、某天突然慢了，可能是什么？（统计信息漂移、执行计划翻转、数据量跨过临界点、缓冲池失效、锁等待、主机 IO 争用）
  • 慢查询日志会不会本身拖慢性能？
  • 除了 SQL 层面，还能从哪些层面优化？（架构、硬件、参数三板斧）

EXPLAIN 输出里最该关注哪些字段？type 和 Extra 的常见值分别意味着什么？
高频必考工具
简答版（30 秒）

重点看五个字段：

  • type（访问类型，性能从好到差）：system > const（主键/唯一键等值）> eq_ref（关联时主键匹配）> ref（普通索引等值）> range（索引范围）> index（扫全索引）> ALL（全表扫描）。线上要求至少 range，ALL 必须优化；
  • key / possible_keys：实际用了哪个索引，NULL 就是没走；
  • rows：预估扫描行数，数量级判断回表代价；
  • Extra：Using index=覆盖索引（好）；Using filesort=额外排序；Using temporary=临时表（这两个出现要警惕）；Using index condition=索引下推；
  • id：相同从上往下执行，不同从大到小（子查询先执行）。
🔍 面试官可能追问
  • Using filesort 一定有性能问题吗？怎么消掉？（联合索引让 ORDER BY 走索引序）
  • index 和 ALL 的区别？（全索引扫描 vs 全表扫描，索引更小但仍是全量）
  • 8.0 的 EXPLAIN ANALYZE 比 EXPLAIN 多了什么？（真实执行 + 每步耗时/行数）

深分页 LIMIT 1000000, 10 为什么慢？怎么优化？
高频必考实战
简答版（30 秒）

LIMIT 1000000, 10 会真实扫描并回表 100 万零 10 行，然后丢掉前 100 万行——慢在「白白回表」。

三种优化，按优先级：

  • 延迟关联（子查询 + 覆盖索引）：先用覆盖索引拿到目标主键，再回表 10 行： SELECT t.* FROM t JOIN (SELECT id FROM t ORDER BY x LIMIT 1000000, 10) tmp ON t.id = tmp.id，扫描全在二级索引上完成，回表只剩 10 次；
  • 游标 / 书签分页：记住上一页最后一条的排序值，WHERE id > ? ORDER BY id LIMIT 10，复杂度 O(1)，但要求连续翻页（适合信息流）；
  • 业务限制：限制最大页数、跳转指定页（产品侧解决，成本最低）。
🔍 面试官可能追问
  • 为什么子查询写法能变快？本质减少的是什么开销？（回表次数）
  • 游标分页排序字段不唯一怎么办？（加 id 做次级排序键）
  • ES / 大数据场景下的深分页问题了解吗？（search_after 与之同理）

什么时候才需要分库分表？怎么选分片键？会带来哪些新问题？
高频必考架构题
简答版（30 秒）

先说克制：单表几百万行、单库未到瓶颈时，优先索引优化 / 读写分离 / 归档冷数据——分库分表是最后手段，不可逆。

  • 什么时候上：单表数据量持续增长导致 B+ 树变高、维护成本剧增（经验值 2000 万级，视行宽而定）；或单实例写入 QPS / 磁盘 / 连接数到物理上限；
  • 拆法：垂直分库（按业务域拆：订单库/用户库）、垂直分表（冷热/大字段分离）、水平分表（按分片键行拆）；
  • 分片键：选查询最高频的等值维度（如 user_id），保证流量均摊、不出现数据倾斜；用基因法或冗余解决跨维度查询（按 user 分片又要按商家查 → 异构索引表 / 宽表）；
  • 新问题：跨分片 JOIN / 聚合（count、分页）、分布式事务、全局唯一 ID（雪花 / 号段）、扩容迁移（一致性哈希 / 双写迁移）。中间件常见 ShardingSphere、MyCat。
🔍 面试官可能追问
  • 分表后全局 ID 怎么生成？雪花算法的时钟回拨问题？
  • 分了 16 张表不够用了怎么扩到 64 张？怎么平滑迁移？（双写 + 存量迁移 + 切读）
  • 不分库分表还有什么替代方案？（TiDB 等 NewSQL 的取舍，你态度可以保守但要说出理由）
